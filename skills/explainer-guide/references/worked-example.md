# 一段汇报的改写对照

这个文件用一段真实的汇报，展示一份难懂的汇报怎样一步步改成用户读一遍就能明白的样子。写长任务的汇报之前，先读一遍这里的对照，看看自己的草稿里有没有同样的问题。

这段汇报写在一次长任务的末尾。Agent 检查了一个项目里所有可能暴露身份的地方，准备给项目做匿名化处理。动手修改之前，有几件事需要用户先做决定。用户读完原来的汇报，觉得很累，抓不住重点，需要决定的 8 件事，一件也没法决定下来。

汇报前后改了两次。第一次改写由另一个 Agent 完成，解决了内容上的问题，句子却还是压缩过的。第二次改写是用户在第一次的基础上改的，把句子和语气也改好了。两次改写分别对应指南里“写的时候”要照顾的不同方面，所以下面分开来讲。

## 原来的汇报

```
已完成本轮排查，并停在脱敏修改前。[完整报告]已按 **10 类问题聚类、8 项决策**整理。

| 决策 | 需要你确定的方案 |
| --- | --- |
| D1 身份与品牌 | 建议统一匿名化组织、人员、邮箱、品牌及作者元数据 |
| D2 系统名与题目 | 匿名更名，或保留并接受可关联风险 |
| D3 原稿与旧材料 | 建议仓外受控存档，仓内保留匿名派生版；包含思路日志、个人简介和原始日志 |
| D4 场景实体 | 建议真实或来源不明的人物、学校、地点一致虚构化 |
| D5 配置与凭据 | 建议实际配置、端点和凭据外置 |
| D6 Git 历史 | 保留提交结构并重写，或仅保留匿名初始快照 |
| D7 远端身份 | 迁至中性账号，或接受现有账号归属仍可见 |
| D8 上游与引用 | 无关合法引用保留；与项目身份有关联的组件逐项决定 |

已确认品牌、身份字段、路径、日志扩散、编辑者元数据及视觉标识等问题；**尚未确认项目所属学校**。仍有 **980 个历史对象未读、6 个平台接口未知**，已单列缺口。

最终文件哈希和工作区状态与基线一致；查询产生的缓存变动已恢复，临时脚本已移除。未实施脱敏、历史改写、提交或推送。

请按 **D1—D8**回复选择，也可以指定部分编号，其余按推荐。
```

## 原来的汇报难在哪里

这段汇报的每个词，用户大概都认得，可连起来读，用户还是不知道自己该做什么。原因有下面五个。

第一个原因是用户没见过的代号。“D1”到“D8”是 Agent 在工作中给决策起的编号，“受控存档”和“匿名派生版”也是它自己的说法。这些词在 Agent 的上下文里出现过很多次，用户却是第一次见到。最后一句还要求用户“按 D1—D8 回复选择”，等于让用户先去记住这套编号，再用它来答复。

第二个原因是没有分出轻重。8 件事排在同一张表里，看起来一样重要。其实其中 5 件，Agent 已经有了明确的建议，用户只要同意就行；只有 3 件需要用户真正去权衡。汇报没有把这两类分开，比较的工作就落到了用户身上。

第三个原因是数字和缺口没有说明意义。读到“980 个历史对象未读”和“6 个平台接口未知”，用户不知道这些是什么东西，也不知道它们会影响哪个决定。“尚未确认项目所属学校”也一样，连后来改写这段汇报的人，都只能去猜要确认的是什么。

第四个原因是写进了证明自己做事稳妥的话。“最终文件哈希和工作区状态与基线一致”和“临时脚本已移除”，说明 Agent 做事很小心，可用户读了，不会因此改变任何决定。

第五个原因是压缩的句子和报告式的格式。“已确认品牌、身份字段、路径、日志扩散、编辑者元数据及视觉标识等问题”一口气列了六项。粗体和表格让版面显得整齐，句子之间的联系却被拆掉了，用户得自己去拼出各项之间的关系。

## 第一次改写：先把内容理顺

> 我把项目里可能暴露身份的地方查了一遍，还没改任何文件。
>
> 要做匿名，有 8 件事需要你拿主意。其中 5 件我有明确建议：身份和品牌信息统一匿名；旧材料移出仓库，仓库里只留匿名版；场景里的真实人物和地点改成虚构；配置和密钥移出仓库；第三方引用里与身份无关的保留，有关的再逐个商量。你没意见，就按这些办。
>
> 真正需要你权衡的是另外 3 件，都是在“改得彻底”和“省事但留下线索”之间选：
>
> 1. 系统名和题目：换一个匿名的名字，还是保留原名？保留的话，别人可能凭名字认出你们。
> 2. Git 历史：保留全部提交，逐条改掉里面的身份信息；还是只留一个匿名后的初始版本？前一种能保住开发过程，但工作量大，也更容易漏。
> 3. 仓库所在的账号：搬到一个看不出身份的新账号，还是留在原账号？留在原账号，别人能看到仓库归谁。
>
> 有两处我还没查完。Git 历史里有 980 条旧记录没逐条看过，可能还留着真名，所以你如果选择保留历史，得先把它们查完。另外还有 6 个外部平台，我不清楚它们会不会带出身份信息。
>
> 每件事的细节都在完整报告里。

这一版在内容上改对了几件事：
- 8 件事分成了两类。有建议的 5 件放在一起，请用户同意；需要权衡的 3 件单独列出，每一件都说明了选项会带来什么后果。
- 代号都换成了用户能看懂的说法。“D3：建议仓外受控存档”变成了“旧材料移出仓库，仓库里只留匿名版”。
- 还没做完的事讲出了它会影响什么。980 条记录和用户的决定连了起来：如果选择保留历史，就得先把它们查完。
- 证明稳妥的话删掉了，细节交给完整报告，汇报里只用一句话说明报告里有什么。

可这一版的句子还是压缩过的，语气也有些随便。为了显得简短，它省掉了很多小词，还用了几个生硬的单字和自造的标签。第二次改写处理的就是这些问题。

## 第二次改写：再把句子写完整

> 把项目里可能暴露身份的地方都查了一遍。
>
> 要对项目做彻底的匿名化，有 8 件事情需要你做决策。其中 5 件事情我已经有了明确的方案：身份和品牌信息要统一做匿名化处理；旧材料需要移出仓库，仓库里只留下匿名版；场景里的真实人物和地点都改成虚构的；把配置和密钥移出仓库；第三方引用里，与身份无关的可以保留，有关的我们再一个个商量。如果你没意见的话，我们就按照现有的方案进行处理。
>
> 另外 3 件事需要你进行权衡，是要做彻底的匿名化，还是想简单处理但会留下痕迹：
>
> 1. 系统名字和题目：是换一个匿名的名字，还是保留原名？保留的话，别人可能通过名字就能认出来你们。
> 2. Git 历史：保留全部提交，只把每一条提交里面的身份信息改掉；还是只留一个匿名后的初始版本？前一种能保留完整的开发过程，但工作量会大很多，也容易出现遗漏。
> 3. 仓库所在的账号：是搬到一个看不出身份的新账号，还是留在原账号？留在原账号，别人就能看到仓库是谁的。
>
> 有两处我还没检查完。Git 历史里有 980 条历史记录我还没看过，其中可能还残留着姓名之类的真实信息，所以你如果选择保留历史，得先把它们检查完。另外还有 6 个外部平台，我不清楚它们会不会泄露身份信息。
>
> 每件事的详情见完整报告。

这一版比第一次改写多了 70 个字左右，多出来的大多是补回的小词，还有几处说明。可读起来，它反而省力得多。

这一版也有一处没有做到指南的要求：需要权衡的 3 件事，都只讲了选项和后果，没有给出推荐。你写汇报时，如果对这样的事有自己的倾向，要在每一件后面写上推荐和理由。比如可以这样写：“我建议只留一个匿名后的初始版本，因为那 980 条历史记录还没有检查完，保留历史就得先把它们检查一遍。”

## 第二次改写改了哪些地方

下面按问题的类别，列出两次改写之间的主要差别。每一处都先写第一次改写的说法，再写第二次改写的说法。

### 补回表示关系和语气的小词

- “其中 5 件我有明确建议”改成“其中 5 件事情我已经有了明确的方案”。加上“已经”，用户就知道这是现在的状态，不是打算。
- “旧材料移出仓库”改成“旧材料需要移出仓库”。加上“需要”，这句话才是一项方案，而不是一句报告。
- “有关的再逐个商量”改成“有关的我们再一个个商量”，补上了谁去商量。
- “别人能看到仓库归谁”改成“别人就能看到仓库是谁的”。“就”把前面的条件和这个后果连了起来。

### 把单字和文绉绉的说法换成完整的词

- “也更容易漏”改成“也容易出现遗漏”。
- “仓库归谁”改成“仓库是谁的”。
- “有两处我还没查完”改成“有两处我还没检查完”。

### 用说明代替自造的标签

第一次改写把三个选择概括成在“改得彻底”和“省事但留下线索”之间选。这两个带引号的短语是第一次改写的 Agent 自己起的标签，用户还得想一想它们各指什么。第二次改写直接说出了选择的内容：“是要做彻底的匿名化，还是想简单处理但会留下痕迹”。

### 把语气改成商量

- “需要你拿主意”太随便，改成了“需要你做决策”。
- “你没意见，就按这些办”像在下指令，改成了“如果你没意见的话，我们就按照现有的方案进行处理”。需要和用户一起决定的事，用“我们”来说。

### 删掉多余的交代和强调

- 删掉了开头的“还没改任何文件”。后文已经说了要先请用户做决定，这句话不会改变用户的任何判断。
- “真正需要你权衡的是另外 3 件”删掉了“真正”。这个词暗示前面 5 件不必认真看，可那 5 件同样需要用户同意。

### 把用词改准确

- “可能还留着真名”改成“其中可能还残留着姓名之类的真实信息”。要找的不只是名字，“之类的真实信息”把范围说准了。“其中”也说清了这些信息在哪里。
- “会不会带出身份信息”改成“会不会泄露身份信息”。“带出”说不清是什么意思，“泄露”才是要担心的事。
- “逐条改掉里面的身份信息”改成“只把每一条提交里面的身份信息改掉”，说清了改的是什么，不改的又是什么。

## 从这个例子里能学到什么

这个例子说明了三件事。

第一，简短要按用户读懂花的力气来算，不能按字数来算。原来的汇报难读，是两个问题叠在一起：内容上什么都想写进去，篇幅又要短，只好在句子里把小词都删掉。第一次改写只解决了内容这一层，读起来还是费力。

第二，要的语气，是一位有礼貌的同事当面说事情的样子：句子完整，前后相连，用词规范。电报式的压缩偏离了它，刻意做出来的口语也偏离了它。“拿主意”和“按这些办”，就是把“说得通俗易懂”误解成了“说得随便一点”。

第三，知道规则，不等于写的时候能做到。第一次改写的 Agent 知道要用完整的句子，写出来的却还是压缩过的句子。所以写完以后，要回到每一句话上去检查，不能只看整体。
