# 怎样把句子写得完整连贯

这个文件讲句子层面的做法。内容选好以后，回复读起来还是费力，问题多半出在句子上：句子压缩过，用户得自己补出省掉的词；或者前后两句接不上，用户得自己去找它们的关系。

下面每一节讲一种问题。每节先说怎样在自己的草稿里认出它，再说怎样改，以及为什么要这样改，最后给出例子；有的小节还会说明适用的边界。各节引用的资料，出处列在文件末尾。

## 不要靠删词来求简短

被要求简短的时候，最省事的办法是把句子里的词删掉。删掉的通常是下面几种：
- 主语，尤其是说明这件事由谁来做的主语。
- 表示时间和语气的词，比如“已经”“就”“会”和“着”。
- 标出句子结构的词，比如“如果……的话”和“是……还是”。
- 双音节词的一个字，比如把“遗漏”写成“漏”，把“决定”写成“定”。

删得厉害的时候，一句话只剩下几个名词和动词，比如“已完成本轮排查，并停在脱敏修改前”。

这样删，句子是短了，读起来却更费力。省掉的东西并没有消失，只是交给了用户去补：这件事是已经做了，还是打算做？这是一项建议，还是已经定下的事？后一句是前一句的结果，还是另一件事？写的人觉得这些关系一清二楚，所以觉得没必要写出来，读的人手里却只有这几个字。当面说话时，听的人可以马上追问。读一条回复时，用户要么自己去猜，要么再发一条消息来问，这比写的人当初多写几个字费事得多。

想控制篇幅，就少讲几件事，讲到的事都用完整的句子讲清楚。句子里只删那些删掉以后意思没有任何损失的词。表示前后关系的词要留着，比如“所以”“但是”和“如果……的话”。表示时间和语气的词也要留着，比如“已经”“还没”和“需要”，它们说明一件事是做完了，还是要去做，或者只是可能发生。用户补不回来的主语要留着，尤其要说清一件事是你做的，还是需要用户做的。读起来像电报的单字，比如“定”和“漏”，要换回完整的词；“改”和“看”这类说话和写文章都常用的单字，可以照常用。

下面是 Agent 回复里的几个例子，每个都先写压缩的说法，再写改好的说法：
- “其中 5 件我有明确建议”，改成“其中 5 件事情我已经有了明确的方案”。
- “前一种……工作量大，也更容易漏”，改成“前一种……工作量会大很多，也容易出现遗漏”。
- “三件事都按你说的定”，改成“这三件事都按照你说的决定下来”。
- “更准确应叫‘默认模型缓存’”，改成“更准确的说法应该是‘默认模型缓存’”。原句把“应该”缩成了“应”，又省掉了“的说法”。
- “它保存模型目录及能力参数”，改成“它保存着模型目录及能力参数”。加上“着”，用户就知道这是文件一直保存着的内容，读起来也像当面说话。
- “中途……的一次编辑被拒”，没有说是谁拒绝了它，为什么拒绝。改好的版本先讲了原因，再写出“因此拒绝了这一次写入”，用户才知道这是一项有意的检查，不是出了故障。
- “原轮结束后可以沿同一会话续聊”，改成“也要等它完成这次作答，才能把修改要求发给它”。“原轮”是把“原来那一轮”压成了两个字。

后四个例子是用户读 Agent 的回复时指出来的。

资料里也有同样的例子。《语法修辞讲话》“苟简”一节收了很多因为少写了词而让人读不懂的句子。其中一句是“一九五〇年是根据一九四九年的实际情况来拟定的”，书里的评语是：“一九五〇年的什么呢？想来应该是‘计划’。”少了“计划”两个字，读者就得自己去猜这句话在说什么。STE（Simplified Technical English，一套英文技术文档的写作规范，最初用于航空维修手册）也明确规定，不要为了缩短句子而省略词语，因为那样句子虽然短了，却不会更好读。它举的例子是把“If installed, remove the shims.”写成“If shims are installed, remove them.”，也就是补回从句的主语。

有些写作规范要求句子短。比如 CTCA 写作风格指南（一份公开的中文技术文档写作规范）建议每句话不超过 40 个字，STE 也给句子规定了词数的上限。这些规定针对的是一句话里塞了好几个意思，它们给出的改法是把长句拆成几句，而不是把词删掉。所以遇到很长的句子，应该拆开来写，每句讲一个意思。

能从上下文毫不费力地补回来的词，可以省。比如连续几句话的主语都是“我”，后面几句就不必每句都写“我”。真正多余的话也应该删掉。《语法修辞讲话》在“苟简”一节的开头，就讲了这里的分寸：“文章不应该烦冗，不必要的话不必说，这是不错的。可是如果走到另一极端，不把话说周全，使意思不能完全表达出来，那也是不对的。”所以判断一个词该不该删，要看删掉以后意思有没有损失：多余的话删掉以后，意思不变；压缩删掉的词，意思会跟着丢掉一部分。

## 不要一句只报一个状态

汇报做完的事时，压缩最常见的样子，是把每件事都缩成一个状态。一个 Agent 按用户的四点要求精简完一份报告，汇报是这样写的（省略号略去的是文件名和数字）：

> 四处精简已完成，已停止。……缩写和编号已补说明，两处重复名单已改链接……数量、链接和文件大小已回读……未改，未提交。

写这条汇报之前，这个 Agent 刚读过这份指南。用户读完的反馈是：“依然存在过于压缩和书面化的情况。‘已停止’ ‘已补说明’ ‘已改链接’。句子和段落之间仍然没有起承转合，内在逻辑不够强。”

这种写法在自己的草稿里很好认：一句话里只有一个动作，前面挂着“已”或者“未”。它有两个毛病。

第一个毛病是书面化。“已”“未”和“仅”这些单字，当面说话时会说成“已经”“没有”和“只”；“现为”会说成“现在是”。它们和上一节讲的“定”和“漏”一样，读起来像电报。

第二个毛病更要紧：几个状态排在一起，彼此没有关系。用户提了几条要求，Agent 就逐条答一句做完了。可每项改动是为了解决什么问题，几项改动合起来让情况有了什么变化，汇报里都没有说，用户只能自己把几句话串起来。

改的时候，要讲清每项改动是为了解决什么问题，做完以后情况有了什么变化，再用“所以”和“这样”这类词把句子连起来。比如不写“三处配置已统一，旧脚本已删除，未提交”，而写“三个服务原来各有一份配置，改一个参数要改三个地方，所以我把它们合成了一份，这样以后只要改一个地方。旧的启动脚本因此用不上了，我也删掉了。这些改动还没有提交，你看过以后我再提交。”

那个 Agent 看到反馈以后重写的汇报，就是这样把改动和它要解决的问题连起来的。用户读完说：“这样读起来就好多了。”不过重写的时候，它把原来的文件名和链接也删掉了，这是另一个问题，见 `layout.md` 的“文件名和链接要留着”。

## 每句话先接上前文，再引出新的内容

读一段话时，用户会期待每句话的开头接着前面说过的内容，句子的后半部分再带来新的信息。如果一句话一开口就是新的东西，用户就得停下来想：这句话和上一句有什么关系？压缩过的汇报常常整段都是这样，每句话各说一件新的事，句子之间没有任何连接。比如下面这段：

> 已确认品牌、身份字段、路径、日志扩散、编辑者元数据及视觉标识等问题；尚未确认项目所属学校。仍有 980 个历史对象未读、6 个平台接口未知，已单列缺口。

这里每一句都从一件新的事开始，用户读完，不知道这几件事之间是什么关系。改好的版本是这样写的：

> 有两处我还没检查完。Git 历史里有 980 条历史记录我还没看过，其中可能还残留着姓名之类的真实信息，所以你如果选择保留历史，得先把它们检查完。另外还有 6 个外部平台，我不清楚它们会不会泄露身份信息。

第一句先告诉用户，接下来要讲两处还没检查完的地方。第二句从第一处讲起，“其中”接着前面的“980 条历史记录”，“所以”又把这些记录和用户要做的决定连了起来。第三句用“另外还有”引出第二处。每句话的开头都接得上前文，用户一路读下去，不用回头去找句子之间的关系。

写的时候，句子的开头放用户已经知道的东西，比如前一句刚提到的事，或者用户自己说过的话；新的信息放到句子的后面。句子之间的关系，用“所以”“但是”和“另外”这类词标出来。段落也是一样，每段的第一句先说这一段要讲什么，后面的句子再展开。

Gopen 与 Swan 在《The Science of Scientific Writing》里讲过读者的这种期待：读者希望句首的内容把这句话和前文连起来，希望句末是这句话要强调的新内容。按他们的经验，新旧信息放错了位置，是美国的专业写作里最常见的问题。他们也提醒，这些原则描述的是读者的期待，不是必须机械遵守的规则，有时有意打破它们，效果反而更好。

## 把指代说清楚

“它”“这”和“其”这样的词，写的人知道指什么，读的人却可能找出两三个对象。省掉了指代的词也会出问题：一句话没有说清它讲的是哪个东西，用户只能去猜。

一个代词可能指两个以上的东西时，就把它换回名词。一句话的对象可能不清楚时，就用“其中”或者“这些记录”这样的词，明确地指回前文。

资料里的例子来自 yikeke 等人的《中文技术文档写作风格指南》“用词恰当”一节。原句是“需要将其 image 字段留空”，“其”指什么不清楚，所以改成了“将相应镜像的 image 字段留空”。Agent 回复里的例子是：“Git 历史里有 980 条旧记录没逐条看过，可能还留着真名”。用户读到“可能还留着真名”，得自己判断是哪里留着。改好的版本加了“其中”，说清了这些信息就在那 980 条记录里。

上下文已经很清楚的时候，不必把每个代词都换成完整的名称，那样反而啰嗦。STE 也只要求在代词有歧义的时候，才把它换回名词。

## 把动作写进动词

一句话里真正发生的动作，有时没有写成动词，而是藏进了名词里。比如“未实施脱敏、历史改写、提交或推送”，以及“对相关配置进行了调整”。用户读到这样的句子，知道发生过某件事，却不知道具体是谁对什么做了什么。

改的办法是找出句子里真正的动作，把它写成动词，再写出是谁做的，对什么做的。“未实施脱敏、历史改写、提交或推送”可以写成“我还没有修改任何文件，没有改写 Git 历史，也没有提交和推送”。用户的第二次改写其实把这句话整句删掉了，因为后文已经说明要先请用户做决定；这里只借它说明怎样把动作写进动词。CTCA 的写作风格指南举过类似的例子：列表里写“网络选项的选择”，不如写“选择网络选项”。Gopen 与 Swan 也说，读者期待由动词来表达句子里的动作；动作没有写进动词，读者就得自己去找。

“进行”本身没有问题。“进行测试”和“进行处理”这样的说法很常见，也不难懂。要改的是“进行”后面跟着一个笼统的名词，把具体做了什么藏起来的情况。比如“对相关配置进行了调整”，用户读了不知道改了什么，应该写成“我把超时时间从 30 秒改成了 60 秒”这样的具体说法。

## 不要把主语和谓语隔得太远

主语后面如果插进一长串修饰或说明，用户读到主语，要等很久才知道它怎么了。比如：“这个被三个模块调用、上周刚改过参数格式的函数，现在会在参数为空时返回 None。”

改的办法是让主语后面尽快出现谓语。插进去的内容如果重要，就单独写成一句，并说清它为什么重要；如果不重要，就删掉。上面的句子可以改成：“这个函数现在会在参数为空时返回 None。它被三个模块调用，上周又刚改过参数格式，所以这三个模块都可能受到影响。”

Gopen 与 Swan 指出，主语和谓语之间插进去的较长内容，读者会把它当作打断，觉得它没那么重要。插入的内容真正重要的时候，这样写会让读者看轻它。

## 不要在名词前面堆修饰语

一个名词前面挂了好几层修饰语，用户得先把这些修饰语都记住，读到最后才知道说的是什么东西。比如：“需要更新所有在上次迁移中被遗漏的仍然引用旧路径的配置文件。”

改的办法是把修饰语拆出来，按事情发生的顺序写成几句：“上次迁移的时候，有一些配置文件被遗漏了，它们还在引用旧的路径。这些文件都需要更新。”

yikeke 的指南“用词恰当”一节处理过这样的句子。原句讲怎样恢复被删除的表，却把“要恢复的是哪一张表”的几个条件，都堆在了句末的“表”字前面。指南的评语是修饰的词组太多，“读起来很拗口，令人费解”。改写以后，句子按先找到那条删除表的语句，再恢复对应的表的顺序展开。STE 也规定名词前面的修饰词不要太多，因为读者得先理解完所有修饰词，才能读到中心的名词。

## 同一个东西始终用同一个叫法

写长回复时，Agent 有时会为了避免重复，或者没有注意，给同一个东西换着用不同的说法。一个 Agent 写过的一段汇报里，“脱敏”和“匿名化”指的是同一件事，可开头说“停在脱敏修改前”，表格里又说“建议统一匿名化”。用户读到两个词，会以为说的是两件事。

一个东西第一次用了什么叫法，后面就一直用它。确实需要换一种说法的时候，要说清楚两个说法指的是同一个东西。STE 规定同一个东西不要用不同的名称。《臺灣易讀參考指南》也要求用词前后一致，它的例子是前面写了“森林”，后面就不要改成“樹林”。

## 并列的内容怎样写

一组并列的内容用了好几个顿号，用户就得一项一项地记，还要自己去想这些项目之间有什么关系。比如：“建议统一匿名化组织、人员、邮箱、品牌及作者元数据”。

一组并列的内容最多用一个顿号。两项并列，用“和”连接；三项并列，写成“甲、乙和丙”。超过三项，可以按关系分成几组，也可以分成几句来写，或者列成列表。还有一种办法，是换成用户关心的那个类别的名称，把细节放进完整的报告。上面那句话，后来就改成了“身份和品牌信息要统一做匿名化处理”。

这条规则是这份指南自己的规定，没有出自外部的资料。它的目的是让用户不必一口气记住一长串项目。
