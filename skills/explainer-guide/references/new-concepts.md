# 给用户讲一个没接触过的概念

这个文件讲怎样给用户讲一个新概念，以及用户没听懂时怎样换个讲法。用户要做一个决定，或者要看懂你做了什么，有时得先明白一个之前没接触过的概念，比如改写 Git 历史意味着什么，或者什么是竞态条件。

`names.md` 讲的是名称：用户不熟悉的名称，怎样换掉，或者用一两句话解释。这个文件讲的是另一种情况：光解释一个名称不够，用户得真正理解一个概念，才能接着往下做。

下面先讲动笔之前要弄清的两件事，再讲怎样讲，最后讲讲完以后怎样判断用户懂没懂，没懂时怎样换个讲法。

## 先弄清用户已经知道什么

讲一个概念要从哪里讲起，取决于用户已经知道什么。Google 的技术写作课程用一个式子来说明这一点：好的文档，等于读者完成任务需要的知识和技能，减去读者已经有的知识和技能。减号后面那一项估计错了，讲解就会出问题：估计少了，用户会觉得你在讲早就知道的事；估计多了，用户会跟不上。

这门课程还提醒，专家常常受到“知识的诅咒”的影响：对一个题目懂得太透，反而会把给新手的讲解弄糟。长时间工作以后，你就处在专家的位置上。你在工作中弄明白的东西，用户大多没有见过。课程还说，读者的范围越宽，就越要假定需要多解释一些。

用户已经知道什么，要从线索来判断：用户在对话里用过哪些词，在自己写的文档里用过哪些词，从这些词又能看出用户熟悉哪些领域。具体的判断方法见 `names.md`。

医生和病人当面谈话时，可以先问对方知道多少再讲。加州大学旧金山分校（UCSF）介绍的“问—讲—问”就是这样：先用开放式的问题了解病人已经知道什么，再根据病人的理解程度来讲，讲的时候用非专业的词，比如说“扩散”而不说“转移”，最后再确认病人听懂了什么。在对话里先问再讲，用户就得多等一轮回复，所以通常还是从线索来判断。只有在这个概念对一个重要的决定很关键，线索又实在不够的时候，才值得先问一句。

## 只讲用户需要的那一部分

一个概念可以讲得很深，可用户需要的，往往只是和眼下这件事有关的那一部分。所以要先想清楚，用户要用这个概念来做什么。

比如用户要决定是否改写 Git 历史。用户需要知道的是：改写以后，从第一条被改动的提交开始，后面所有提交的编号都会变；已经下载过这个仓库的人得重新下载，而且他们手里的旧副本仍然保留着原来的历史。至于 Git 内部怎样保存这些记录，和这个决定没有关系，就不用讲。

## 从用户熟悉的东西讲起

讲一个新概念，最好先从用户熟悉的一个具体例子讲起，等用户看懂了例子，再说出概念的名字和一般的道理。

华罗庚写《统筹方法》，就是这样讲的。他没有从定义讲起，而是先讲泡茶：要洗水壶，烧开水，洗茶壶茶杯，拿茶叶，最后泡茶。他列出三种办法，其中一种是“洗好水壶，灌上凉水，放在火上；在等待水开的时间里，洗茶壶、洗茶杯、拿茶叶；等水开了，泡茶喝。”读者自己就能看出，这种办法最省时间。他算出来，这种办法总共要 16 分钟，另外两种要 20 分钟。讲完以后他才说：“这是小事，但这是引子，可以引出生产管理等方面有用的方法来。”

用到 Agent 的回复里，比如要给用户讲竞态条件，可以这样写：“两个程序同时修改同一个文件，就像两个人各自下载同一份表格，改完再上传，后上传的人会把前一个人的修改覆盖掉。程序里的这种问题叫作竞态条件。”先讲用户熟悉的情形，再给出名字，用户就知道这个名字指的是什么。

## 用类比的时候，讲清楚对应关系和不像的地方

类比是讲新概念的常用办法，可它也容易把用户带偏。Glynn 研究教学中的类比时说，类比是一把双刃剑：它能帮助理解，也能造成误解。

只说一句“A 就像 B”，帮助不大。Glynn 举的例子是“细胞就像一座工厂”。这样一句话，没有说清细胞的哪一部分对应工厂的哪一部分，读者不知道该怎样理解。好的类比，要把两边的部分一一对应起来。比如用水流来讲电路：水管对应导线，水泵对应电池，水压对应电压，水管变窄的地方对应电阻。

类比还要讲清楚不像的地方。Glynn 介绍的教学方法里，有一步专门用来指出类比在哪里不成立。他举的例子里，老师用万有引力定律来讲库仑定律，讲完相同的地方以后，又提醒学生，引力只会相互吸引，电荷之间的力却既可能吸引，也可能排斥。不讲不像的地方，用户就可能把类比里的特点，当成新概念本来就有的特点。

用到 Agent 的回复里，比如用“文档的副本”来讲 Git 的分支：在分支上提交，不会影响主分支，就像在副本上修改，不会影响原件；把分支合并回主分支，就像把副本上的修改抄回原件。不像的地方在于，合并时 Git 会自动合并两边改动的不同位置，只有两边改了同一个地方，才需要人来决定保留哪一边。

如果概念本来就很简单，就不必用一个复杂的类比。Glynn 也说，对比较简单和直接的概念，详细的类比可能是不必要的。

## 一次只讲一小步

一个概念如果包含好几个新的部分，就一次讲一部分，讲清楚了再讲下一部分。Rosenshine 总结课堂教学的研究时说，人的工作记忆很小，一次只能处理很少的几项信息，一下子讲得太多，学生就会被弄糊涂。所以更有效的老师一次只讲一小部分新内容，学生掌握了这一步，才讲下一步。他举的例子是教学生概括一个段落：先教找出段落的话题，再教找出主旨，最后教找出支持主旨的细节，每一步都先示范，再让学生练习。

用到回复里，就是不要在一句话里引出好几个新的名词。比如用户需要先明白“分支”，才能明白“合并冲突”，就先讲分支，说清楚它和眼下这件事的关系，再讲冲突。

一步一步地讲，会多用一些字。Rosenshine 也说，按小步来教是需要时间的，更有效的老师花在讲解新内容上的时间更多。这和 `content.md` 里讲的一致：衡量回复是否简短，要看用户读懂花了多少力气，而不是字数。

## 讲完以后，怎样知道用户懂了

讲完以后，不要用“有不清楚的地方随时问我”或者“这样讲清楚了吗？”来结束回复。这样的问题，几乎没法让你知道用户懂没懂。Rosenshine 总结的研究里，效果较差的老师只是问一句“有什么问题吗？”，没有人提问，就以为学生都学会了。美国卫生保健研究与质量局（AHRQ）的健康素养工具包也说，“你明白了吗？”这类问题，病人不管懂没懂，都很可能回答“明白了”。

在书面的回复里，你看不到用户的反应，所以要从用户接下来的消息来判断。用户用自己的话正确地说出了这个概念，或者根据它做出了合理的决定，说明用户懂了。用户的问题如果暴露出误解，就说明前面的讲解有地方没讲清楚。AHRQ 的工具包还提醒，对方只是把你的原话重复一遍，不一定说明听懂了。

不要为了确认用户懂没懂，就要求用户把概念复述一遍。医生可以这样请病人复述，可在工作中这样要求用户，会显得你把用户当成了学生。

## 用户没听懂的时候，换一个讲法

用户没听懂的时候，不要把原来的解释再说一遍，也不要只是说得更长。AHRQ 的工具包要求，发现病人有误解时，换一种办法再讲一遍，再确认一次。原来的讲法既然没有讲通，再说一遍多半还是讲不通。

换讲法之前，先从用户的话里找出误解在哪里，然后只针对这一处来讲。可以换一个具体的例子，换一个类比，或者从更前面的一步讲起。比如你讲了改写 Git 历史，用户回复问：“那我的代码会不会丢？”这说明用户把“改写历史”理解成了改动代码本身。这时不用再讲一遍提交编号会变，而要直接回答这个误解：“你现在的代码不会丢。改写历史改的是过去的提交，比如提交里的作者姓名和邮箱，以及旧版本文件里的身份信息；最新版本的代码会原样保留。”

AHRQ 的工具包里记录了一位医生的体会：他让一位母亲复述刚才交代的事情，对方说不出来，他这才意识到，自己一心想着把信息讲出去，没有发现对方根本没有接收到。长时间工作以后，你也很容易处在这样的状态里。所以用户的回复里一旦出现没听懂的迹象，就要停下来，先把这一处讲通，再往下推进。
