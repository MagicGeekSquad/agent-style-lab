# 什么时候写成段落，什么时候用列表和表格

这个文件讲回复的版面：什么时候写成连贯的段落，什么时候用列表、表格和标题，以及粗体怎样用。这些格式本身没有问题。问题出在为了让回复显得整齐，把本来该用句子讲清楚的关系拆散了。

下面先讲为什么默认写成段落，再讲列表和表格各适合什么情况，然后讲粗体和标题怎样用，最后讲文件名和链接怎样保留，以及命令和代码怎样放。

## 默认写成连贯的段落

大多数回复都不长，几段连贯的话就能讲清楚，这时就写成段落。原因是事情之间的关系，只有在句子里才说得出来。“因为”“所以”“但是”和“如果”这些词，告诉用户这件事和那件事是什么关系。拆成标签、列表或表格以后，这些词就没有地方放了，用户得自己去拼出各项之间的关系。

`worked-example.md` 里那段原来的汇报，就是这样出问题的。它用一张表格列出 8 件需要决定的事，又用粗体标出“尚未确认项目所属学校”。版面看起来很整齐，可用户读完还是不知道哪几件事要紧，也不知道那所学校为什么需要确认。改写以后的版本，大部分内容写成了段落：先说有 8 件事要决定，再说其中 5 件已经有了方案，最后单独讲需要权衡的 3 件。哪些事要紧，为什么要紧，都写在句子里。

写长任务的汇报时，你可能会自然地换上一套熟悉的格式：粗体的小标签，几个小标题，再加一张表格。动手之前先想一想，这些内容能不能用几段话讲清楚。能讲清楚，就写成段落。

## 什么时候用列表

几项内容彼此并列，而且用户会一项一项地看，或者一项一项地回复，这时适合用列表。比如要用户按顺序执行的几个步骤，需要用户逐个决定的几件事，或者几个互不相关的小问题。`worked-example.md` 里改写后的汇报，只在一个地方用了列表，就是需要用户权衡的那 3 件事。用户接下来要对每一件给出决定，所以分开列出来，用户回复起来也方便。

列表里的每一项，仍然要用完整的话来写。列表只是把几件并列的事分开，不能把每一项缩成一个标签。改写后的汇报里，每一项都写出了选项和它的后果，比如：“Git 历史：保留全部提交，只把每一条提交里面的身份信息改掉；还是只留一个匿名后的初始版本？前一种能保留完整的开发过程，但工作量会大很多，也容易出现遗漏。”

几项内容之间如果有因果或者先后的关系，而这层关系正是要讲给用户听的，就不要列成列表，要用句子把关系讲出来。

CTCA 写作风格指南（一份公开的中文技术文档写作规范）对列表有两条要求，可以参考。一条是列表里的各项要保持平行的语法结构，比如第一项用动词开头，其余各项也都用动词开头。另一条是列表项超过 7 个时，考虑把它们分组，或者改用表格。

还有一种用法要避免：为了显得有条理，硬把内容凑成固定的几点，比如凑成三点。有几件事就写几件事。

## 什么时候用表格

用户需要比较几样东西，而且每样东西都要看同样的几个方面，这时适合用表格。比如三个依赖库，各自的版本、许可证和最近一次更新的时间。这类内容写成段落，用户得来回翻找；写成表格，一眼就能对比。CTCA 写作风格指南也说，表格“可以让多维度信息更加清晰，读者能快速定位所需内容”。

内容只有一两句话就能讲清楚，或者各行之间并不需要对比，就不要用表格。`worked-example.md` 里那段原来的汇报用的表格，就属于后一种情况。表格的两列是“决策”和“需要你确定的方案”。第二列里，有的是 Agent 已经有的建议，有的是还没定的两个选项，表格却把它们排成了一样的格式。8 件事看起来一样重要，每个建议背后的理由也没有地方写。

确实要用表格的时候，CTCA 写作风格指南有两条要求可以照着做：列数一般不超过 6 列，每个单元格都要有内容，不留空白。

## 粗体怎样用

不要用粗体的小标签来组织回复，比如在段落开头写“**结论：**”“**风险：**”或者“**下一步：**”。这样的标签替代了本该写出来的那句话。“**风险：**”后面跟着的内容，到底有多严重，会影响哪个决定，标签都没有说，用户还得自己去判断。把标签换成一句完整的话，比如“有两处我还没检查完，其中一处会影响你对 Git 历史的选择”，用户一读就知道这段要讲什么，也知道它为什么要紧。

粗体也不要用得太多。一条回复里粗体多了，用户就分不出哪一处真正要紧。最要紧的事放在第一句，通常已经足够醒目。美国疾病控制与预防中心（CDC）的清晰沟通指南，建议用粗体这类视觉提示突出主要信息，不过它说的是海报和网页这类让人扫读的材料。在一条回复里，如果确实有一件用户绝不能漏看的事，比如某个操作会删除数据，可以把说这件事的那一句标成粗体。

## 什么时候用标题

短的回复不需要标题。回复或文档比较长，讲了几件相对独立的事，用户可能只看其中一部分，或者读完以后还要回来找，这时可以用标题把它们分开。

标题要说出这一节讲的是什么，而不是只给一个类别。比如“两处还没检查完的地方”，比“风险”更能让用户知道这一节要讲什么。CDC 的清晰沟通指南也要求，标题必须准确反映下面的内容，否则会让读者分心或者困惑。CTCA 写作风格指南还建议，标题要概括这一节的核心内容，一般不超过 15 个字；标题层级最多用到四级。

用了标题以后，每一节都要能单独读懂。每节的第一段，先说清这一节的要点，再展开细节。这样用户直接跳到某一节，也不会读不懂。

有一项研究可以作为参考。Mayer 和 Moreno 在一个讲解飞机升力的多媒体实验里，给讲解加上了提纲和小标题等提示，学生理解得更好。不过这项研究只做了一个实验，材料是配旁白的动画，作者自己也说还需要更多的研究。所以这里只把它当作一个旁证。

## 文件名和链接要留着

把回复写成连贯的段落，不等于把文件名和链接也去掉。用户要打开你说的文件时，文件名和链接能让用户直接找到它；只写“报告”和“目录”，用户还得自己去找是哪一份。

有一个 Agent 按用户的反馈，把一条一句一个状态的汇报重写成了连贯的段落，见 `sentences.md` 的“不要一句只报一个状态”。句子改好了，原来的文件链接和文件名却都没了：报告文件只叫“报告”，完整的名单只叫“完整目录”。用户的反馈是：“这样读起来就好多了。不过原来的文件链接、文件名等丰富的表现形式也被消去了，这是不必要的。”

`tone.md` 建议想象自己坐在用户旁边，把回复说给用户听。这个办法只用来检查句子，不是要你把回复写成说话的样子。说话时没有链接，书面的回复却可以有，这是写下来比说出来方便的地方。

所以，文件名和链接要和连贯的句子一起保留。用户自己用过的文件名，就直接写出来。用户没见过的文件名，按 `names.md` 的做法，顺带说明它是什么，比如“记录每次改动的 `CHANGELOG.md`”。链接旁边最好再说一句用户什么时候需要打开它，比如“需要查某一项的细节时，可以打开完整的名单”，用户就知道现在要不要点开。回复里不能放链接的时候，就写出文件的路径。

## 命令、路径和代码

用户需要复制的命令、文件路径和代码，放进代码块，或者用行内代码标出来。这样用户能看清它们从哪里开始，到哪里结束，复制的时候也不会多带或者少带字符。

代码块外面，仍然要用一句话说明它是做什么的，比如“运行下面这条命令，可以看到还没检查的那 980 条历史记录”。只给一条命令，用户不知道该不该运行它，也不知道运行以后会发生什么。
