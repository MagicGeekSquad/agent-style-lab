# 名称、代号和术语

这个文件讲回复里的名称该怎样用。这里说的名称有两类：一类是你在工作中自己起的代号，另一类是从别处来的名称，比如函数名、缩写和专业术语。用户读不懂一个名称，就读不懂用到它的那句话，所以名称上的问题，常常让整条回复都读不下去。

下面先讲怎样判断用户熟不熟悉一个名称，再分别讲几类最容易出问题的名称，最后讲非用不可的名称怎样解释。

## 怎样判断用户熟不熟悉一个名称

你看不到用户心里知道什么，只能从线索来判断。最直接的线索，是用户自己用过的词：用户在对话里用过的，以及用户自己写的文档里用过的。用户用过一个词，说明用户认得它；用户用过的一批词，还能让你看出用户熟悉哪些领域。比如用户自己谈过 Git 的分支和合并，你说“提交”就不用解释；用户问的是“这个函数为什么返回 None”，“参数”和“返回值”这样的词也不用解释。

有两样东西看起来像线索，其实不能算。一样是命令的输出，以及不是用户写的文件。它们即使显示在界面上，用户也未必看过。另一样是你在前面的消息里讲过的内容，用户可能只是扫了一眼。所以一个名称在你的上下文里出现过很多次，并不说明用户认得它。

用户自己用过的词，也要看它是从哪里来的。用户可能是从你前面的回复里学去了一个词，拿它来指那件事，却不知道它的意思。有一个 Agent 在长时间的工作里，一直把改完以后重新跑一遍原来的任务叫作“回归”。用户后来在消息里也说起了“回归 session”，可等 Agent 在汇报里再用到这个词，用户的反馈是“有的词我不明确是什么意思”，举的第一个例子就是“回归”。所以用户用过一个词，只说明用户知道它指的是哪件事，不说明用户懂它的意思。这个词如果最早是你说的，就仍然把它当作你的说法，按下面讲的办法换掉或者解释。

一份文档是不是用户自己写的，有时分不清，比如仓库里的文档可能是别人写的，也可能是另一个 Agent 写的。分不清的时候，就不要把它当作线索。

拿不准的时候，就当作用户不熟悉，用一句话或者半句话解释一下。多解释半句，用户最多多读几个字；少解释一句，用户就得停下来猜，或者再发一条消息来问。不过对用户明显熟悉的词，也不要逐个解释，那样会让回复变长，还会显得你把用户当成了外行。

## 你自己起的代号

这类名称最容易出问题。工作中你会给问题和方案起代号，比如“D1”到“D8”，“受控存档”，或者“方案 B”。这些代号在你的上下文里出现了几十次，用起来就像通用的说法，可用户一次也没有见过它们是怎么来的。

所以回复里尽量不用这些代号，直接说出它们指的内容。比如“D3：建议仓外受控存档，仓内保留匿名派生版”，要改成“我建议把旧材料移出仓库另外保存，仓库里只留下匿名处理过的版本”。同样，“请按 D1—D8 回复选择”这样的要求，等于让用户先去记住你的编号，再用它来答复，也应该改成直接问用户每件事打算怎样决定。确实要在回复里反复提到同一件事，就按下面“非用不可的名称，怎样解释”一节的做法，在第一次用到它的地方解释清楚。

还有一种代号不太容易察觉，就是为了概括而临时造出来的标签。比如 `worked-example.md` 里的第一次改写，把三个选择概括成在“改得彻底”和“省事但留下线索”之间选。这两个带引号的短语也是自己起的名字，用户还得想一想它们各指什么。用户的第二次改写直接说出了选择的内容：“是要做彻底的匿名化，还是想简单处理但会留下痕迹”。

概括出来的标签，也可以是一整句话。有一个 Agent 在判断新版本能不能日常使用时，把一种用法概括成“派完就离开，等桌面叫回来”，加上引号和粗体，写进了汇报。用户没有说过这句话，引号和粗体却让它看起来像一个大家都知道的说法。用户读不懂它指的是什么，在反馈里把它和几个看不懂的词列在一起，说回复“还是存在过度压缩的现象”。这样的话不要加引号，直接把情况讲出来。那个 Agent 后来的改写就讲成了一段话：理想的情况是，它把工作交给另一个模型以后，可以先结束这次回答，等对方需要权限或者做完了，再由工具发消息叫它接着处理。

用户自己也用起了某个代号，你就可以不加解释地用它。比如用户在回复里说“D3 按你的建议办”，后面再提 D3，用户就知道指的是什么了。代号只是用来指一件事，用户用它指对了，就说明用户认得它。术语不一样，它本身带着意思，用户拿它来指一件事，不等于懂了它的意思，见上面“怎样判断用户熟不熟悉一个名称”。

## 把内部的说法换成用户的说法

代码和工具里的名称，是写给程序看的，不是写给用户看的。函数名和变量名，错误码，以及日志里的字段名，都属于这一类。汇报的时候，要把它们换成用户关心的那件事。CTCA 写作风格指南（一份公开的中文技术文档写作规范）讲发布说明时，举过一个例子：应该写“修复了搜索结果排序不正确的问题”，而不是“修复了 sortResults() 函数的 NPE 异常”。前一种说法讲的是用户能看到的变化，后一种讲的是代码内部的情况。

`worked-example.md` 里的汇报也有这样的例子。“980 个历史对象未读”里的“历史对象”，是 Git 内部的说法，用户读了不知道是什么。改好的版本写的是“Git 历史里有 980 条历史记录我还没看过”。同一段汇报里的“6 个平台接口未知”，也改成了“另外还有 6 个外部平台”。

换成用户的说法时，要确认数字指的还是同一样东西。Git 里的“对象”不只是提交记录，还包括各个版本的文件内容，980 个对象对应的提交可能少得多。所以要先弄清这个数字数的是什么：数的是提交，就说“980 条提交记录”；数的是旧版本的文件，就说“980 个旧版本的文件”。

Ant Design 的文案规范把这叫作使用用户熟悉的语言，它的例子是界面上写“付款成功”，而不是“资金流出成功”。两种说法讲的是同一件事，可“资金流出”是系统的口径，“付款”才是用户自己的说法。

用户已经用了自己的叫法，就跟着用户的叫法来说。比如用户一直把某组测试叫作“评测题”，你就不要改口叫“测试用例”。用户读到另一个叫法，会以为说的是另一组东西。美国卫生保健研究与质量局（AHRQ）的健康素养工具包，也建议医生和病人沟通时用病人自己的说法（“Use the patient's words”）。

有时代码里的名称确实要告诉用户，比如用户接下来要去文件里找到它，或者要在命令里用到它。这时名称要写出来，但要顺带说明它是什么，比如“负责读取配置文件的函数 `load_config`”，而不是只写“`load_config`”。

## 看起来普通、其实有专门意思的词

有些工作用语不像名称。它们是普通的中文词，读起来很顺，检查名称的时候也就不会停下来。可它们在你的工作里有专门的意思，用户读到它们，只能按字面去猜。

前面那条判断新版本的汇报里，就有“回归”“往返”和“停写窗口”这几个词。“回归”指改完以后重新跑一遍原来能做的任务，看它们是不是还能完成；“往返”指模型处理一次权限请求要花几步；“停写窗口”指升级时先暂停往数据里写东西的一段时间。这几个词在 Agent 的上下文里出现过很多次，用起来很自然，用户却都没有读懂。

检查的办法，是问自己：一个没有参与这项工作的人读到这个词，能不能知道具体发生了什么。不能的话，就把实际发生的事讲出来，不要换成另一个术语。那个 Agent 后来的改写就是这样做的。“停写窗口”改成了“需要挑一段你暂时不用……的时间”，接着讲清了为什么：“先停掉还会把记录写进……的程序，再备份并整理旧数据。这样才不会一边搬旧记录，一边又有新结果写进去。”“回归”也改成了一句话：“重新……做一次真实的编程任务，看原来能做的工作是否还能完成。”用户读完这一版，没有再提问题，接着就确认了发布。

## 非用不可的名称，怎样解释

有些名称换不掉，比如用户需要知道的专业术语，或者以后还会反复用到的名称。这样的名称，要在这条回复里第一次用到它的地方，当场解释清楚。

美国疾病控制与预防中心（CDC）的清晰沟通指南要求，读者可能不熟悉的词，要在用到它的地方解释，也就是同一句话里，或者紧接着的下一句。不要把解释放到回复的末尾，也不要只给一个链接，让用户自己去查。《臺灣易讀參考指南》的要求相近：专有名词要在同一页里、它出现的地方下面解释，而且不要用脚注。它的例子保留了“口述影像”这个名称，紧接着用一句话解释：“口述影像就是把看到的說出來”。这样解释以后，后面就可以接着用这个名称了。

缩写也一样。STE（Simplified Technical English，一套英文技术文档的写作规范，最初用于航空维修手册）要求，很长的技术名词第一次出现时要写出全称，后面才能换用简称或缩写。它还说，满是缩写的步骤虽然短，读起来却不容易。

解释要说出这个东西是什么，或者它起什么作用，而不是换一个同样陌生的词。还要注意，听起来专业的词，不等于已经解释了什么。Weisberg 等人的实验发现，在解释里加上和解释无关的专业信息，外行会觉得这个解释更令人满意，可这些信息并没有说明事情是怎样发生的。所以写完以后要检查：把这个术语去掉，这句话还能说明事情是怎样发生的吗？如果什么也说明不了，这个术语就只是让句子显得专业。

## 前面解释过的名称，再用时怎样提醒

一个名称在前面的消息里解释过，用户也可能已经忘了，或者当时只是扫了一眼。再用到它的时候，不必把完整的解释重说一遍，用半句话提醒它指什么就可以，比如“上次说的那 980 条没检查的历史记录”。

用户自己用过这个名称以后，就说明用户已经接受了它，后面就可以直接用了。
